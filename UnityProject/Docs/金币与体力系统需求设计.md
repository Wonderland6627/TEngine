# 金币与体力系统需求设计

## 一、需求概述

基于README.md中的3个简单想法，扩展出完整的金币与体力系统需求，建立游戏的经济主循环，提升玩家留存和游戏深度。

---

## 二、金币系统（Coin System）

### 2.1 核心需求

**目标**：建立游戏的经济主循环，让玩家有持续的游戏目标和资源管理策略。

### 2.2 金币获得方式

#### 2.2.1 推关奖励（主要来源）

**需求描述**：
- **胜利奖励**：通关关卡后根据关卡难度给予基础金币奖励
  - 第1-3关：50-100金币（新手友好）
  - 第4-6关：100-200金币（中等难度）
  - 第7-10关：200-300金币（高难度）
  - 后续关卡：按关卡ID递增，每关+50金币
  
- **星级奖励**：根据通关表现给予额外金币（未来扩展）
  - 3星通关：额外50%金币
  - 2星通关：额外25%金币
  - 1星通关：基础金币

- **首次通关奖励**：首次通关某关卡时，给予双倍金币奖励

**技术实现思路**：
- 在 `World.CheckGameOver()` 中，当玩家胜利时调用 `AddCoinReward(levelId, isFirstTime)`
- 创建 `CoinManager` 单例类，管理金币的增减和同步
- 金币奖励配置可放在 `LevelConfig` 中，或独立的 `CoinRewardConfig.json`
- 使用事件系统 `GameEvent.Send(SlimeEvent.OnCoinChanged, coinAmount)` 通知UI更新

#### 2.2.2 签到奖励（每日稳定来源）

**需求描述**：
- **每日签到**：每天首次登录可签到，获得金币奖励
  - 第1天：50金币
  - 第2天：60金币
  - 第3天：70金币
  - 第4天：80金币
  - 第5天：100金币
  - 第6天：120金币
  - 第7天：200金币（周奖励）
  - 第8天起：循环第1-7天的奖励

- **连续签到奖励**：连续签到7天额外获得500金币

**技术实现思路**：
- 创建 `CheckInManager` 管理签到逻辑
- 在 `UserGameInfos` 表的 `checkIn` 字段中记录签到信息
- 云函数 `checkIn` 处理签到逻辑，返回奖励金币数量
- 客户端调用签到接口后，更新本地金币并同步到云端

#### 2.2.3 宝箱奖励（额外来源）

**需求描述**：
- **每日宝箱**：每天可开启1次免费宝箱，获得随机金币（50-150金币）
- **看广告宝箱**：观看广告后可额外开启1次宝箱（100-200金币）
- **成就宝箱**：完成特定成就后获得宝箱奖励（未来扩展）

**技术实现思路**：
- 创建 `TreasureBoxManager` 管理宝箱系统
- 在 `UserGameInfos` 表中记录每日宝箱开启状态
- 宝箱奖励使用随机数生成，范围可配置
- 与广告系统集成，观看广告后解锁额外宝箱

### 2.3 金币消耗方式（未来扩展）

- **锦囊刷新**：使用金币刷新锦囊列表（每次50金币）
- **体力购买**：使用金币购买体力（100金币=10体力）
- **道具购买**：购买游戏内道具（未来扩展）

### 2.4 数据存储

**数据库字段**：
- `UserGameInfos.coin`：用户当前金币数量（Number，默认0）
- 需要原子操作更新，使用 `db.command.inc()` 增加金币

**本地存储**：
- `SlimeGameData` 中添加 `coin` 字段，与云端同步
- 启动时从云端拉取最新金币数量

## 三、体力系统（Energy System）

### 3.1 核心需求

**目标**：限制玩家的游戏频率，增加游戏粘性和付费点，同时保证玩家体验。

### 3.2 体力值规则

#### 3.2.1 基础设定

- **初始体力**：100点
- **体力上限**：100点（未来可通过VIP或道具提升）
- **推关消耗**：每关消耗10点体力
- **体力恢复**：每5分钟恢复1点体力（即100点需要500分钟≈8.3小时）

#### 3.2.2 体力获得方式

**每日赠送**：
- **每日重置**：每天0点重置体力至100点（如果当前体力<100）
- **每日额外赠送**：每天首次登录额外赠送20点体力（上限不超过100）

**时间恢复**：
- **自动恢复**：每5分钟恢复1点体力，直到达到上限
- **恢复时间记录**：记录上次恢复时间，计算离线期间恢复的体力
- **恢复逻辑**：
  ```csharp
  // 伪代码
  int offlineMinutes = (当前时间 - 上次恢复时间) / 60;
  int recoveredEnergy = Mathf.Min(offlineMinutes / 5, energyMax - currentEnergy);
  ```

**其他获得方式**（未来扩展）：
- 观看广告恢复：每次观看广告恢复20点体力（每天限3次）
- 金币购买：100金币=10点体力（每天限5次）
- 好友赠送：好友可赠送体力（每天限1次）

### 3.3 体力扣除规则

#### 3.3.1 推关前扣除

**需求描述**：
- **扣除时机**：在 `World.StartGame(levelId)` 之前检查并扣除体力
- **扣除数量**：每关固定消耗10点体力
- **不足处理**：
  - 如果体力不足，弹出提示窗口："体力不足，需要10点体力"
  - 提示窗口提供选项：
    - "观看广告恢复20点体力"（如果当天未达到上限）
    - "使用100金币购买10点体力"（如果当天未达到上限）
    - "等待恢复"（显示恢复时间倒计时）
    - "取消"

**技术实现思路**：
- 在 `UILevelWindow` 的关卡选择按钮点击时，先检查体力
- 创建 `EnergyManager` 单例类，管理体力的增减和恢复逻辑
- 修改 `World.StartGame()` 方法，在开始游戏前调用 `EnergyManager.TryConsumeEnergy(10)`
- 如果体力不足，返回false，显示体力不足提示窗口
- 体力扣除成功后，再执行原有的游戏开始逻辑

#### 3.3.2 体力恢复逻辑

**需求描述**：
- **实时恢复**：游戏运行时，每5分钟自动恢复1点体力
- **离线恢复**：玩家离线后再次登录时，计算离线期间恢复的体力
- **恢复上限**：体力不能超过上限（100点）

**技术实现思路**：
- 在 `World_GameData.cs` 中记录 `lastEnergyRecoverTime`（最后恢复时间）
- 使用 `GameModule.Timer` 创建定时器，每5分钟检查并恢复体力
- 启动时计算离线恢复：`CalculateOfflineEnergyRecovery()`
- 体力变化时发送事件：`GameEvent.Send(SlimeEvent.OnEnergyChanged, energyAmount)`

### 3.4 数据存储

**数据库字段**：
- `UserGameInfos.energy`：当前体力值（Number，默认100，范围0-100）
- `UserGameInfos.energyMax`：体力上限（Number，默认100）
- `UserGameInfos.energyRecoverTime`：最后恢复时间（Date，可选）
- `UserGameInfos.lastEnergyResetDate`：最后重置日期（String，YYYY-MM-DD）

**本地存储**：
- `SlimeGameData` 中添加 `energy`、`energyMax`、`lastEnergyRecoverTime` 字段
- 启动时从云端拉取最新体力数据，并计算离线恢复

在玩家点击开始游戏时，先检查体力是否足够，如果足够则扣除体力并开始游戏，如果不足则提示玩家。

### 4.2 交互流程

```
玩家点击关卡开始按钮
    ↓
检查体力是否 >= 10
    ↓
是 → 扣除10点体力 → 开始游戏
    ↓
否 → 显示体力不足提示窗口
    ↓
提供恢复体力的选项（广告/金币/等待）
```

## 六、云端同步方案

### 6.1 数据同步时机

**金币同步**：
- 获得金币时：推关胜利、签到、开宝箱后立即同步
- 消耗金币时：购买体力、刷新锦囊后立即同步
- 启动时：从云端拉取最新金币数量

**体力同步**：
- 扣除体力时：推关前扣除体力后立即同步
- 恢复体力时：每5分钟恢复后同步（或批量同步）
- 每日重置时：每日重置后同步
- 启动时：从云端拉取最新体力数据，并计算离线恢复

### 6.2 云函数设计

**现有云函数扩展**：
- `getUserGameInfoV2`：返回用户数据时包含 `coin` 和 `energy` 字段
- `setUserGameInfoV2`：支持更新 `coin` 和 `energy` 字段

**新增云函数**（可选）：
- `consumeEnergy`：扣除体力（原子操作）
- `addCoin`：增加金币（原子操作）
- `checkIn`：签到并增加金币（原子操作）

### 6.3 数据一致性保证

- 使用原子操作：`db.command.inc()` 和 `db.command.dec()` 保证数据一致性
- 客户端先更新本地数据，再同步到云端（乐观更新）
- 如果云端同步失败，回滚本地数据或提示用户

## 九、注意事项

1. **数据安全**：所有金币和体力的增减必须在云端验证，防止客户端作弊
2. **性能优化**：体力恢复使用定时器，避免频繁的云端同步
3. **用户体验**：体力不足时提供多种恢复方式，避免玩家流失
4. **数值平衡**：金币和体力的数值需要根据实际游戏体验调整
5. **兼容性**：新用户默认体力100，金币0；老用户需要数据迁移
