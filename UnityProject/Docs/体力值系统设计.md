## 一、系统概述

体力值是玩家进入关卡所需的消耗资源，用于控制玩家的游戏频率，提升游戏粘性。

**核心功能**：
- 进入关卡前消耗体力值（客户端判断）
- 每日登录赠送体力值（客户端判断）
- 通过看广告和开宝箱获得体力值（客户端主导）

**设计原则**：
- **客户端主导**：所有体力值的增减由客户端计算和判断
- **服务端校验**：客户端传入变化量，服务端校验并返回是否成功和修改后的值
- **配置驱动**：所有数值配置放在JSON中，客户端启动时读取
- **事件驱动**：UI通过事件广播更新，不直接耦合

## 二、基础规则

### 2.1 基础数值（配置在JSON中）

| 项目 | 数值 | 说明 | 配置位置 |
| :--- | :--- | :--- | :--- |
| **体力上限** | 150点 | 体力值不能超过此上限 | 服务端常量 + 客户端JSON |
| **每日登录赠送** | 50点 | 每天首次登录赠送，赠满150为止 | 客户端JSON |
| **关卡消耗** | 10点/关 | 每次进入关卡消耗的体力值 | 客户端JSON |
| **看广告奖励** | 配置值 | 看广告获得的体力值 | 客户端JSON |
| **宝箱奖励** | 配置值 | 开宝箱获得的体力值 | 客户端JSON |

### 2.2 配置JSON结构

**文件路径**：`Assets/AssetRaw/Configs/jsons/energy_config.json`

**配置内容**：
```json
{
  "energyMax": 150,
  "dailyLoginReward": 50,
  "levelConsume": 10,
  "adReward": {
    "min": 20,
    "max": 30
  },
  "chestReward": {
    "min": 10,
    "max": 20
  }

```

### 2.3 体力值获取方式

#### 方式1：每日登录赠送（客户端判断）
- **触发时机**：游戏启动时，客户端检查是否满足每日赠送条件
- **赠送规则**：赠送50点，赠满150为止（如果当前体力 + 50 > 150，则只赠送到150）
- **判断逻辑**：客户端比较本地日期和上次登录日期，决定是否赠送
- **示例**：
  - 当前体力100，登录后变为150（100 + 50）
  - 当前体力120，登录后变为150（120 + 30，只赠30点）

#### 方式2：看广告奖励（客户端主导）
- **触发时机**：玩家观看广告后
- **奖励数量**：根据配置随机获得20-30点
- **上限处理**：客户端计算，如果增加后超过150点，则设置为150点
- **同步**：客户端计算变化量，调用服务端接口校验

#### 方式3：开宝箱奖励（客户端主导）
- **触发时机**：玩家开启宝箱时
- **奖励数量**：根据配置随机获得10-20点
- **上限处理**：客户端计算，如果增加后超过150点，则设置为150点
- **同步**：客户端计算变化量，调用服务端接口校验

## 三、核心流程

### 3.1 进入关卡流程（客户端判断）

```
玩家点击关卡开始按钮
    ↓
客户端检查当前体力值是否 >= 10（从配置读取）
    ↓
是 → 客户端计算扣除10点 → 调用服务端接口校验 → 进入关卡
    ↓
否 → 广播事件（OnEnergyNotEnough）→ UI层处理提示
```

**说明**：
- 进入关卡的判断完全在客户端完成
- 客户端计算变化量（-10），调用服务端接口校验
- 服务端校验成功返回新值，客户端更新本地数据并广播事件

### 3.2 每日登录赠送流程（客户端判断）

```
游戏启动
    ↓
客户端从服务器拉取用户信息（getUserGameInfoV2）
    ↓
客户端检查最后活跃时间（lastActiveAt）
    ↓
如果日期已变化 → 客户端计算赠送50点（赠满150为止）
    ↓
客户端调用服务端接口校验变化量
    ↓
服务端校验成功 → 返回最新体力值 → 客户端更新本地数据 → 广播事件
```

**说明**：
- 每日登录赠送由客户端判断和计算
- 客户端比较本地日期和服务器返回的 `lastActiveAt` 日期部分
- 客户端计算变化量，调用服务端接口校验
- 服务端校验成功返回新值，客户端更新并广播事件

### 3.3 看广告/开宝箱奖励流程（客户端主导）

```
玩家看广告/开宝箱
    ↓
客户端从配置读取奖励范围（如20-30点）
    ↓
客户端随机计算奖励数量
    ↓
客户端计算增加体力值（考虑上限150）
    ↓
客户端调用服务端接口校验变化量
    ↓
服务端校验成功 → 返回最新体力值 → 客户端更新本地数据 → 广播事件
```

**说明**：
- 奖励计算完全在客户端完成
- 客户端计算变化量，调用服务端接口校验
- 服务端校验成功返回新值，客户端更新并广播事件

## 四、数据存储

### 4.1 数据库字段（UserGameInfos 表）

| 字段名 | 类型 | 默认值 | 说明 |
| :--- | :--- | :--- | :--- |
| `energy` | Number | 150 | 当前体力值（0-150） |
| `lastActiveAt` | Date | null | 最后活跃时间（完整时间信息） |

**说明**：

## 七、服务器接口

### 7.1 获取用户信息接口

**接口名**：`getUserGameInfoV2`

**功能**：
- 返回用户当前体力值和最后登录日期
- 不处理每日登录赠送（由客户端判断）

**响应数据**：
```json
{
  "code": 0,
  "data": {
    "energy": 150,
    "lastActiveAt": "2024-01-15T10:30:00.000Z"
  }
}
```

### 7.2 更新体力值接口（服务端校验）

**接口名**：`updateEnergy`

**功能**：
- 客户端传入体力值变化量，服务端校验并返回结果
- 服务端校验：检查变化后的值是否在有效范围内（0-150）
- 校验成功则更新数据库，返回最新值；校验失败则返回错误

**请求参数**：
```json
{
  "change": 20,
  "source": "ad_reward"
}
```

**参数说明**：
- `change`：体力值变化量（正数为增加，负数为减少）
- `source`：体力值变化来源（daily_login / ad_reward / chest_reward / level_consume）

**响应数据（成功）**：
```json
{
  "code": 0,
  "data": {
    "energy": 150,
    "success": true
  }
}
```

**响应数据（失败）**：
```json
{
  "code": -1,
  "msg": "Energy out of range",
  "data": {
    "energy": 100,
    "success": false
  }
}
```

**服务端校验逻辑**：
```javascript
// 伪代码
const ENERGY_MAX = 150; // 服务端常量
const currentEnergy = userGameInfo.energy;
const newEnergy = currentEnergy + change;

// 校验：新值必须在 0-150 范围内
if (newEnergy < 0 || newEnergy > ENERGY_MAX) {
  return {
    code: -1,
    msg: "Energy out of range",
    data: {
      energy: currentEnergy, // 返回当前值，不更新
      success: false
    }
  };
}

// 校验通过，更新数据库
userGameInfo.energy = newEnergy;
return {
  code: 0,
  data: {
    energy: newEnergy,
    success: true
  }
};
```

## 九、实施要点

### 9.1 客户端主导原则

- **所有判断**：进入关卡、每日登录赠送等所有判断都在客户端完成
- **计算变化量**：客户端计算体力值变化量，调用服务端接口校验
- **配置驱动**：所有数值从JSON配置读取，启动时加载
- **事件驱动**：UI层通过事件广播更新，不直接耦合

### 9.2 服务端职责

- **体力上限**：保存为常量 `ENERGY_MAX = 150`，用于校验
- **校验变化**：校验客户端传入的变化量，确保结果在有效范围内（0-150）
- **返回结果**：校验成功返回新值，校验失败返回当前值和错误信息

### 9.3 配置加载

- **启动时加载**：客户端启动时从 `energy_config.json` 读取配置
- **配置缓存**：配置加载后缓存在 `EnergyManager` 中
- **配置更新**：如需更新数值，修改JSON文件即可，无需改代码

### 9.4 体力值同步流程

- **启动时**：
  1. 从服务器拉取最新体力值和 `lastActiveAt`
  2. 客户端判断是否需要每日登录赠送（比较 `lastActiveAt` 的日期部分）
  3. 如需要，计算变化量并调用服务端接口校验
  4. 服务端返回最新值，客户端更新并广播事件

- **进入关卡**：
  1. 客户端判断体力是否足够
  2. 如足够，计算变化量（-10）并调用服务端接口校验
  3. 服务端校验成功返回新值，客户端更新并广播事件
  4. 如不足，广播 `OnEnergyNotEnough` 事件

- **看广告/开宝箱**：
  1. 客户端计算奖励数量
  2. 计算变化量并调用服务端接口校验
  3. 服务端校验成功返回新值，客户端更新并广播事件

- **同步失败处理**：
  - 如果服务端校验失败，客户端保持当前值，不更新
  - 下次启动时从服务器拉取最新值

### 9.5 事件广播机制

- **事件定义**：在 `SlimeEvent.cs` 中定义事件常量
- **广播时机**：体力值变化时广播 `OnEnergyChanged`，体力不足时广播 `OnEnergyNotEnough`
- **UI监听**：UI层监听事件，收到事件后更新显示
- **解耦设计**：UI层不直接调用 `EnergyManager`，只监听事件

## 十一、注意事项

1. **数值平衡**：体力消耗和获取的数值需要根据实际游戏体验调整，修改JSON配置即可
2. **客户端判断**：所有判断都在客户端完成，服务端只做校验
3. **服务端校验**：服务端校验变化后的值是否在有效范围内（0-150），防止异常数据
4. **事件驱动**：UI层通过事件广播更新，不直接调用 `EnergyManager`
5. **兼容性**：新用户默认体力150，老用户需要数据迁移（将 `energy` 字段更新为150）
6. **配置管理**：所有数值配置在JSON中，便于调整和热更新
7. **简化逻辑**：客户端主导所有逻辑，服务端只做校验，减少服务端压力
